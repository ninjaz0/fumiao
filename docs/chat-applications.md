# Original chat adoption

`OriginalChatApplications.apply` implements the pinned `POST /api/chats/{cid}/apply` contract in PostgreSQL. The [original chat HTTP controller](chat-http.md) uses it when `API_PROTOCOL=original` is selected. Clients sign in to the NestJS instance with their migrated account to obtain a session for that instance. The default site still uses the pinned Python backend for chat.

The service validates input, selected workspace/conversation access, canvas access and cross-workspace scope, then checks UID replay before optimistic revision and message validation. Complete assistant messages remain eligible when superseded; message lookup is scoped to the conversation. New nodes and replacement preserve the original text, positioning, titles, edges and response shape.

One transaction locks the conversation, then the canvas, then the UID and writes the raw bytea document, revision/editor/time, media/pack references, node index, canvas-chat relation and adoption audit. Existing migration 020 retains `project_public_id` while deletion nulls the optional canvas FK. Replays match the permanent public identity; deleted canvas access still fails before replay, as in the original. A concurrent soft deletion that acquires the conversation lock first is observed before any canvas write. An invalid canvas identifier returns the original 404. Appending to a 200-node canvas retains the original internal document-validation failure.

The sole shared canvas change exposes its existing `nodes(sql, project, document)` synchronizer so adoption uses the current transaction. Save/copy implementation is unchanged.

Validation:

- `pnpm test` includes a native adoption regression covering the permanent identity, bytea NUL/Unicode, hidden complete messages, node indexing, UID replay, isolation and actual canvas deletion history. A separate test creates a conversation, sends and settles its first turn through a versioned fixture plugin, then verifies adoption, node-scoped conversation lookup and unchanged billing after replay.
- `STUDIO_PYTHON=<original venv python> pnpm test:chat-applications` runs an isolated FastAPI/SQLite oracle loaded from the verified production manifest and exact full-response/error comparisons, then native rollback and concurrency checks. Persisted adoption audits and canvas-chat links are also compared to the original SQLite export. Set `TEST_DATABASE_URL` to an isolated test PostgreSQL instance to exercise real concurrent connections; the helper creates and drops a random schema. Without it PGlite is used, which serializes transactions and cannot prove PostgreSQL contention.
- Oracle cases cover both modes, expected text/revision ordering, invalid input, message role/state/conversation, superseded replies, 12000/12001 Unicode code-point limits, NUL, the 200-node boundary, sticky/image/deleted targets, empty and anchored/capped positions, edges, workspace and private access, soft deletion, and removal of nodes/references through save.
- PostgreSQL checks cover same UID and target, fresh same UID with different targets, distinct UIDs at the same revision, a concurrent soft deletion and a late audit trigger failure restoring raw document bytes, revision, timestamps, media/pack references, node index, audits and links, followed by a retry with the same UID, stale reference reconciliation, actual canvas deletion and valid historical imports with live/orphaned adoption replay, plus replay after restoring a permanent canvas identity whose historical FK remains NULL. No providers, payments or production database are used.
