## 现有实现对重构的约束

- `generation.py` 和 `image_api.py` 根据模型名称分派给 Flow、Muse 或本地执行逻辑，新增提供方需要修改中央分支。
- `model_policy.py`、`credits.py`、`chat_models.py` 和 `node_models.py` 分别维护模型、权限、价格与硬件目录，新增模型涉及多个文件。
- `image_api.py`、`muse_provider.py`、`flow_provider.py` 和 `chat_runtime.py` 各自处理执行和恢复，覆盖同步返回、异步轮询、流式对话与任务结果不确定等不同语义。
- `core.py` 负责 SQLite、存储和初始化。积分冻结、成功扣减、失败退款与任务状态事务关联，`credits.py` 中的数据库触发器参与结算。
- 前端由原生 `static/studio.js` 和 React/TypeScript 画布、对话模块组成，已有构建入口位于 `canvas`。
- H3 和 Breeze 使用节点登记、心跳、任务租约及媒体回传。插件协议需要容纳节点主动领取任务的执行方式。

相关入口见 [任务创建](../generation.py)、[模型策略](../model_policy.py)、[积分结算](../credits.py)、[服务启动](../image_api.py)、[节点协议](../worker_api.py) 和 [画布构建](../canvas/package.json)。

## 技术栈候选

两条路线共用下文的插件协议和迁移验收条件。

| 维度 | 方案 A | 方案 B |
| --- | --- | --- |
| Web 前端 | 统一为 React 和 TypeScript，复用画布及对话模块 | 统一为 React 和 TypeScript，复用画布及对话模块 |
| 业务后端 | Python 和 FastAPI，重组为按业务领域划分的模块 | TypeScript 和 NestJS，逐域接替已有 API |
| 模型和媒体执行 | 独立 Python 执行进程，按协议连接插件 | TypeScript 或 Python 插件服务，GPU 与媒体处理继续使用 Python 和 FFmpeg |
| 插件协议 | JSON Schema 与 HTTP，流式结果使用 SSE | 同一套协议 |
| 现有逻辑复用 | 可直接复用大部分权限、账本和任务逻辑 | 通过兼容层复用，迁移过程中逐项移植与对照 |
| 主要工作量 | 拆分依赖、整合队列、统一前端与插件注册 | 包含 A 的边界整理，并增加跨语言 API、数据访问和恢复逻辑迁移 |
| 适用目标 | 尽快交付插件能力，同时改善工程结构 | 将平台业务代码长期统一为 TypeScript，并接受更长迁移周期 |

根据现有源码的复用程度，方案 A 可以作为默认候选。若业务层统一 TypeScript 是明确目标，则选择方案 B。先用一个真实现有提供方完成插件契约试点，再确定最终路线。

React 前端可沿用 Vite。若产品主页需要服务端渲染或索引能力，可将 Next.js 纳入前端选型。前端框架、数据库和队列分别作决定，实施顺序按各自验收结果推进。

数据库先复用 SQLite 及现有事务行为。进入多进程写入和业务服务迁移阶段时，评估 PostgreSQL。队列可先由数据库任务记录驱动独立执行进程，后续按吞吐与运维需求引入 Redis 和对应任务队列。积分余额、冻结额和流水应在同一持久数据库事务内变更，派发使用事务性 outbox，Redis 承担调度与缓存职责。

原高校平台设计基于空仓库提出全栈 TypeScript。当前已导入完整平台源码，技术选型需要重新计入现有权限、账本、节点协议及恢复逻辑的迁移成本。原设计中 Redis 冻结与数据库结算分开的部分，应在实施设计中统一事务边界。

## 模型提供方插件架构

### 系统职责

平台核心负责身份、工作区、资产访问、模型开放策略、定价、积分、任务状态和审计。执行协调层负责领取任务、并发限制、派发、恢复、取消和结果入库。提供方插件负责把标准请求翻译成上游协议，并返回标准状态、产物和用量。

工作台和画布从公共模型目录读取能力与参数，向统一任务服务提交。任务服务完成授权、输入固定和积分冻结，随后由执行协调层选择已登记的插件实例。插件返回的产物经平台校验和保存后，再进入成功结算。

### 插件和连接实例

分开保存四种标识。

| 对象 | 用途 | 示例 |
| --- | --- | --- |
| 插件类型 | 定义接入协议与执行代码 | `openai-compatible-chat`、`flow`、`muse`、`gpu-node` |
| 连接实例 | 配置地址、凭据、并发、配额和适用空间 | 同一个插件可登记两套不同账号或网关 |
| 模型 | 提供稳定的平台模型标识 | 关联一个连接实例和上游模型标识 |
| 模型规格 | 定义具体能力、参数限制与定价档位 | 分辨率、时长、参考输入模式、采样设置 |

已有 `MiniMax H3`、`muse-video`、`flow:*` 等标识通过兼容映射保留。历史作品、价格记录和旧客户端继续使用已有标识，新目录保存清晰的插件与连接关系。

### 插件声明

插件随版本提供 manifest，至少包含以下字段。

- 稳定的插件 ID、插件版本、契约主版本、显示名称。
- 支持的模态与执行方式，包含文本、图片、视频、语音，以及立即返回、异步任务、流式输出、节点领取。
- 配置字段和凭据字段的 JSON Schema，凭据字段带有私密标记。
- 模型列表或模型发现能力、规格清单、输入输出 Schema、默认值及能力限制。
- 支持查询、取消、幂等提交和恢复查询的能力标记，以及相应语义。
- 健康检查、并发建议和超时策略。

采用 JSON Schema 2020-12 描述配置和模型参数，并在确定语言后生成相应类型和校验器。主界面可据此生成常见参数控件，H3 首尾帧等专用交互使用显式控件类型及标准化槽位描述。[JSON Schema 规范](https://json-schema.org/draft/2020-12)

### 执行契约

| 操作 | 内容 | 适用范围 |
| --- | --- | --- |
| `describe` | 返回插件、模型和能力声明 | 全部插件 |
| `health` | 返回可用状态与脱敏诊断 | 全部插件 |
| `submit` | 接收固定输入与幂等键，返回已完成、已受理或提交结果待确认 | 请求型插件 |
| `inspect` | 按上游任务 ID 或支持的幂等键查询状态 | 支持异步或恢复查询的插件 |
| `cancel` | 请求取消并报告取消结果 | 声明支持取消的插件 |
| `stream` | 输出文本增量、完成状态和用量事件 | 流式插件 |
| `claim`、`heartbeat`、`complete` | 领取任务、续租与提交产物 | GPU 节点桥接插件 |

同步图片请求可以在 `submit` 中返回产物。Flow 和 Muse 可返回上游任务标识并继续查询。对话采用带序号的流式事件。GPU 桥接插件复用现有节点协议，再逐步统一内部状态。

事件携带平台任务 ID、执行尝试 ID、事件 ID 和序号。产物包含媒体类型、尺寸或时长、内容校验信息及临时读取引用。平台保留已处理事件记录，以唯一约束和状态版本校验处理重复、乱序和延迟消息。

### 任务与计费一致性

1. 提交事务固定工作区、输入资产、模型规格、价格版本、插件版本、连接配置版本和凭据引用版本，同时写入任务、冻结记录和待派发事件。
2. 执行进程通过租约领取事件。每次派发创建独立尝试，调用使用固定幂等键，记录上游请求 ID 和任务 ID。
3. 网络错误按已确认拒绝、可安全重试、已受理、提交结果待确认分类。待确认记录进入恢复查询或人工核对流程，保存上游可能已计费的事实。
4. 已知生成完成但下载失败的任务继续保存已有产物。下载重试复用上游产物引用。
5. 平台校验并保存产物后，在事务内推进终态并结算一次。迁移期间沿用现有 `jobs` 终态与账本触发器，新增尝试表记录更细的执行状态。
6. 取消先记录意图，再按插件能力协调。上游完成与取消并发时，通过同一状态版本和唯一结算记录确定平台结果，同时记录上游实际状态。
7. 停用插件实例后停止新派发，已有执行按固定版本继续恢复和完成。卸载前排空任务并保留历史模型描述。

### 安装与运维

插件管理提供安装、登记连接、测试连接、启用、停用、升级和排空状态。安装新版本后验证契约兼容性，存量任务继续绑定原版本。升级切换按连接实例进行。

第一版可把官方适配器作为随平台发布的包，注册机制独立。随后增加独立进程或容器插件，允许 Python 和 TypeScript 实现同一 HTTP 契约。Python 包发现可使用标准 entry points，FastAPI 生命周期可用于登记执行资源并在退出时释放。[Python 插件发现](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/) [FastAPI 生命周期](https://fastapi.tiangolo.com/advanced/events/)

第三方插件进程使用分配到当前任务的输入与凭据引用，平台管理数据库、钱包和工作区授权。插件出错、重启或超时由执行协调层处理。凭据解引用和媒体访问使用受限的服务端接口，日志按字段脱敏。

## 分阶段迁移

### 第一阶段 统一开发基线

整合 GitHub 增量与线上依赖、Flow 管理认证及 TLS 补丁、Muse 发送修复。建立源码提交、依赖锁定和构建制品之间的对应关系。核对 GPU 包内部源码，统一显存阈值和 Colab 安装行为。

验收包括现有平台回归、Flow 与 Muse 的补丁回归、GPU 安装包清单校验。完成后产出可重复构建的本地开发版本和差异处理记录。

### 第二阶段 固定插件协议并完成试点

交付 manifest Schema、任务输入输出 Schema、错误与恢复语义、注册表、模型目录及契约测试。先用模拟提供方验证安装与配置，再包装现有 Muse 适配器。保留现有 Muse 执行和恢复逻辑，先迁移登记及分派入口。

验收要求新增一个模拟插件后，模型能出现在目录中并通过现有工作台或画布入口提交，接入过程使用注册机制。覆盖同步、异步和流式三类契约，以及重复提交、超时待确认、重复完成、跨空间引用和插件停用。

在这个试点完成后，结合迁移代码量、类型生成体验和运维成本，确定方案 A 或 B。

### 第三阶段 迁移全部现有提供方

依次迁移 Muse、Flow、对话、图片和 GPU 节点。模型目录、权限与价格从插件声明及平台配置关联生成。旧接口转换请求后进入相同任务服务，保留历史模型别名和幂等键映射。

每个提供方独立灰度，以隔离工作区验证任务创建、恢复、取消、产物保存和账本结果。已有幂等键映射需要同时查询旧记录，避免旧客户端重试创建第二个任务。

### 第四阶段 迁移工程结构和业务模块

方案 A 将现有后端重组为身份与空间、资产、账本、任务、模型目录、插件运行时等模块，并将执行进程与 Web 进程分离。

方案 B 先搭建 TypeScript 业务服务和兼容路由，再逐域接替旧 API。迁移顺序从目录和只读查询开始，随后是资产与任务，最后处理钱包与支付。NestJS 的模块系统可承载领域模块和显式依赖关系。[NestJS 模块](https://docs.nestjs.com/modules)

前端按工作区、模型设置、生成表单、作品和管理页逐步统一到 React。画布与对话组件持续复用，模型选择和参数表单读取同一能力目录。

### 第五阶段 数据迁移与生产切换

若选择 PostgreSQL，先在隔离数据集上迁移并核对用户、空间、任务、资产引用、余额、冻结额、流水和支付订单。旧库继续承载尚未迁移的业务域，每张表明确唯一写入方。

正式切换前先排空需要迁移的队列，再暂停相关写入，完成最终增量迁移及核对后切换。数据库提交与任务派发通过 outbox 衔接。新系统产生写入后，回滚路径需要能够接续这些记录并处理已受理的上游任务。

生产灰度按提供方和工作区推进。验收覆盖旧客户端、在途任务、重复回调、支付到账、权限撤销和媒体访问。每次发布保存源码提交、依赖锁定、插件版本、数据库版本与制品哈希。

## 首个可交付里程碑

完成开发基线整合，并通过现有页面接入一个使用注册机制的模型插件。管理员能登记连接、配置凭据、启停提供方和查看健康状态。任务完整经历授权、输入固定、冻结、派发、产物保存和结算，失败与恢复路径有可重复的隔离测试。

技术栈决策以该里程碑的试点结果为依据。可分别评审前端统一方式、业务后端语言和数据库迁移时机。
