# 原对话存储与执行迁移

本阶段增加独立 PostgreSQL 会话、消息、轮次、计费和任务发件箱，以及 BullMQ 后台执行。提供方通过已冻结版本的 `chatStream` / `chatTitle` 插件执行；会话领域不按 DeepSeek、OpenAI 等名称分支。

**尚未切换默认应用。** `/studio` 的对话仍由原 Python 后端处理。新会话服务暂未挂载发送 HTTP 路由；原会话完整历史已支持原子导入并通过对照；HTTP/SSE、画布采用及 React 对话交互仍需作为相关契约继续迁移。原工作台/画布 JavaScript 和固定 UI 基线没有变更。不能把本阶段视作完整对话或全栈迁移完成。

## 数据与事务

`019_original_chat.sql` 建立独立的 `chat_conversations`、`chat_messages`、`chat_turns`、`chat_charges`、`chat_outbox`、`canvas_chat_links` 与 `chat_applications`，不复用开发原型的媒体任务或 `documents(kind=chat)`。画布链接和采用历史已支持导入，采用写入逻辑尚未实现。后续 `020_original_chat_import.sql` 允许采用记录保留已删除画布的公开编号，活动画布外键可空；消息仍须属于同一会话。

内部 UUID 外键与原公开编号明确分开：会话/轮次公开 ID 为 32 位十六进制，消息为安全整数。原浮点秒时间、软删除、隐藏的失败回复、原用户消息和原上下文分别保存。标题、消息及错误使用 UTF-8 bytea，保留 PostgreSQL text 不支持的 U+0000；孤立代理项按原 SQLite UTF-8 绑定行为失败。上下文和整数用量保留原 JSON 文本，包含大于 JavaScript 安全整数的计数。

发送在一个事务内完成权限、重复 UID、修订、目录/凭据、并发上限、消息上限、画布上下文、价格及钱包校验，随后写入消息、轮次、冻结积分、账本和发件箱。插件版本、连接配置与价格均冻结；密钥保持加密。全局准入锁保证跨实例仍遵守每用户 3 轮、全局 20 轮的原限制。模型、钱包与画布锁按固定顺序获取。

停止、成功、失败和恢复共用一次终结事务，锁定会话/轮次/费用后结算。重复或迟到结果不能再次扣款、退款或增加修订。重试复用原用户消息及上下文，并隐藏旧的未完成回复；新传入的上下文仍先检查修订和权限。删除、恢复、团队协作及个人空间隔离沿用原规则。

## 后台执行与恢复

`apps/worker` 同时运行独立的 `fumiao-chat` BullMQ 队列。PostgreSQL 发件箱是真实待执行记录，Redis 只负责唤醒。入队失败不丢失冻结记录；发件箱在 5 秒后可再次投递。多个派发器、重复 BullMQ 投递和丢失 Redis 待执行键均由数据库归属控制，不会重复请求提供方。

执行器原子领取轮次，保存 60 秒租约，每秒续期并检查停止状态。领取过的轮次不会重新请求提供方；过期归属按原“服务重启，回复已停止，积分已退回”状态恢复。另一个正常进程的有效租约不会被恢复。尚未领取的发件箱可以继续执行，因为没有发生提供方请求。这个设计替代了原单进程启动时中断全部运行轮次的做法，避免横向扩容时中断其他实例。

回复由服务端持有，不依赖浏览器连接。保留原 600 秒整体超时、0.15 秒部分文本写入间隔、50000 Unicode 字符限制、完整回复判定、失败说明和退款。显式停止保留最后已落库的可见部分，清空用量/结束原因；关闭当前执行进程则保留其内存部分。任何失效租约的进度或终结写入都被拒绝。数据库故障后未成功结算的轮次通过租约恢复，不自动再次请求提供方。

只有首条用户消息成功完成且未手动改名、未删除的会话会请求标题。标题请求有独立 15 秒时限；写入再次检查标题和用户改名/删除状态，只增加修订，不改变更新时间。标题失败不撤销已完成的回复或扣费。

对上游非法对象/数组结束原因，原运行器的 SQLite 绑定会失败并留下运行轮次；对照验证保留这一边界，随后由租约恢复退款。尚需继续覆盖其他非字符串结束原因的 SQLite 数值文本转换，再接通完整 HTTP 路径。

## 完整原会话历史导入

导出文件新增 `chatVersion: 1`，包含会话原 rowid 顺序、全部消息（含隐藏回复）、全部已结算轮次、费用、画布链接和采用记录。公开编号、发送 UID、浮点时间、标题状态、修订、用量 JSON 文本和上下文不重写；新消息编号及会话排序序列推进到旧上限后。历史轮次不附加凭据、插件配置、租约或发件箱，因此不会恢复成待执行任务。旧 UID 重放仍只返回当前历史，不再次冻结积分。

导入前核对表完整性、用户/空间归属、消息与回复/轮次关联、费用终态、两笔冻结/结算账本及钱包归属。活动轮次、冻结费用、缺失消息/账本或跨空间关联会中止；不会推测缺失回复或费用。账号、钱包、对话及关联账本处于同一 SQL 事务，末尾失败会全部回滚。相同指纹重试不覆盖之后的恢复、改名或新消息；同来源变更仍被拒绝。

对话原始归档写入带空间归属的 `legacy_chat_records.payload` UTF-8 bytea，完整保留 U+0000 文本。新导入不再生成只含可见消息的通用 `documents(kind=chat)`，已有开发库的通用文档保持原状。此前不含轮次和采用记录的导出不能据归档自动补全；CLI 要求重新导出到新的隔离目标库，不修改旧库或执行增量双写。

画布删除后采用记录仍保留 `project_public_id`，其活动外键置空；画布链接按原级联删除。节点被移除时，链接和采用历史继续保留，不要求节点当前存在。完整画布迁移仍待实现；现有画布 JSONB 投影对 U+0000 节点/标题的无损处理也须随原画布文档存储一起完成，本轮对话历史验证不能替代该验收。

## 验证与剩余边界

- `pnpm test:chat-storage`：真实原 FastAPI/SQLite 的 86 个场景，对照新服务响应以及每步完整会话、消息、轮次、费用、钱包、账本和画布链接；涵盖校验顺序、原错误、幂等、重试、权限和回滚。
- `pnpm test:chat-runtime`：真实原运行器的 26 个场景、58 份中间/最终快照，对照上下文请求、流式节流、用量、停止、错误、长度限制、标题竞态和恢复后的账本。提供方仅使用可控本地事件，传输本身由既有 181 个提供方对照场景覆盖。
- `pnpm test:chat-import`：从真实原 API 构造并导出 5 段对话、14 条消息、8 个轮次与费用、2 个链接、3 个采用记录，逐字段核对原编号和状态；导入后的 30 个读取、权限、恢复、改名、旧 UID 重放、重试/停止操作与原服务对照。另验证四种导出拒绝条件。随机 PostgreSQL schema 和临时 PGlite 均通过。
- `pnpm test` 新增 3 组历史导入测试，包括 21 种不完整/不一致输入、后段数据库故障的完整回滚、并发与重复导入、私有空间隔离、删除画布后的采用审计，以及大整数/NUL 文本保存。
- `pnpm test` 中另有 12 组数据库/执行测试，包含 PostgreSQL 并发准入、竞争终结、跨实例停止、过期归属、真实 Redis 入队恢复与重复投递。未设置 `TEST_REDIS_URL` 时只跳过 Redis 组，其余可使用临时 PGlite。

测试使用随机 PostgreSQL schema、临时 SQLite/PGlite 和随机 Redis 队列，不使用用户数据、线上凭据、真实模型或支付。

后续必须补齐 HTTP/SSE 的身份与空间检查、完整画布文档存储/验证及修订保护，并覆盖运行器非字符串结束原因的数值转换。已有通用历史归档不能替代新版本完整导出和新表迁移。完成后才可替换原对话路径，并在等数据、等主题、等视口下继续逐项验证 React 工作台。
