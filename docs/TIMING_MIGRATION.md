# 任务计时迁移

已实现 TypeScript 估算引擎和 PostgreSQL 执行记录，并接入 Advanced 执行器与 GPU v2 网关。这是原任务/状态迁移的一部分；排队预测引擎已通过[独立对照](QUEUE_MIGRATION.md)，原 `/api/state`、提交预估与工作台尚未切换到这些实现。

## 插件能力

Muse、Flow、GPU、图片插件新增不可变的 `1.2.0` 版本。`manifest.timing` 声明像素/原生比例匹配、硬件隔离、采样步数缩放和工作流别名；纯函数 `timingFeatures` 提取模型特征。核心估算器不维护提供方名称或型号名单。

已有 `1.0.0` / `1.1.0` manifest 不变，新数据库目录仍先注册 `1.1.0`。新版本须通过已有显式升级/目录激活流程启用；已接受任务继续使用原版本快照。尚未升级的版本不会获得伪造的计时特征。

`timingFeatures` 当前是受信任的本地插件能力，远程 HTTP 插件尚无对应的特征协议。`Execution.reportTiming` 是可选的本地进度函数，不发送到远程服务。图片 `1.2.0` 在提交时报告生成阶段。Muse `1.4.0` 新增 `timing.providerClock` 及 `Execution.reportProviderClock`，用上游排队/开始时间分离接收与执行；安装后仍须显式激活。Flow 尚未提供可靠的阶段进度，继续保留不确定预测。

## 执行记录

`013_job_timing.sql` 保存任务 UUID、独立执行编号、尝试次数、插件/策略快照、阶段时间、采样进度、预测和受限机器描述。计时特征不包含提示词、参考文件 URL、提供方配置、节点凭据或任务租约。

执行器和 GPU 网关在持有任务行锁时更新记录。异步提供方的轮询继续同一次计时；重复回传不能重新结算积分。租约恢复保留已观察到的时间，并将恢复完成的记录排除出校准样本。worker 进度阶段不会倒退，重复/倒序采样进度不会追加，错误采样步数不更新进度；异常长的 worker 区间不会覆盖已接受的区间。提供方绝对时间单独按原同步规则处理。

GPU v2 心跳新增可选 `context`（硬件/运行时描述）和 `report`（`job_phase`、`step`、`steps`、`uploading`、`timing`）。报告必须同时携带当前 `jobId` / `lease`；过期租约不会写入计时。已有 v2 worker 仍能工作，但内置 Python 桥接 worker 尚未发送完整机器/采样遥测，原 worker 端点和并行通道协议也尚未迁移。服务器仍可记录领取及结果验证/完成时间。

历史估算保留原全局最近 500 条有效/旧样本边界、相似度、冷/热启动隔离、步数缩放、同实例校准、加权分位数和完成尾时。保留 Python 的偶数舍入，以及 Python 3.12 权重求和行为，避免边界误差选中不同样本。

## 提供方绝对时间

Muse `1.4.0` 在提交及轮询后报告受限时间字段，核心按当前任务租约和已接受的计时策略更新同一执行记录。上游明确排队时清空执行开始时间并保留首次接收时间；已开始时采用有效的上游开始/生成/完成时间。只接收创建前两秒至服务器当前时间后两秒内的阶段时间，并将开始时间夹到任务创建之后。缺少有效开始时间的完成响应可用上游更新时间减耗时回推，保留原来源说明和数值边界。

不会把提供方整段响应、提示词或凭据写入计时。无效时间值不作为时钟；仅保留原算法需要的“上游曾报告开始/生成”的布尔区别，避免错误清除已观察阶段或改变来源说明。阶段、接收时间及回推规则与固定原实现对照。worker 的单调区间报告与提供方绝对时间使用不同的严格 schema；本地回调不发送给远程 HTTP 插件。

`1.0.0`–`1.3.0` Muse 请求/回执行为保持不变，新能力只属于 `1.4.0`。轮询复用原执行记录与已接受的配置，过期租约/终态任务的回调不能写入，不会因此重发生成请求或再次结算。

## 历史迁移

完整导出现在包含 `job_runs` 白名单字段，排除旧 `run_key`，不导出节点表和实时提供方任务。仍有运行中计时记录时拒绝导出。导入与原账号/任务在同一事务中完成，重新生成执行键，将旧任务/节点编号映射为稳定 UUID，保留尝试顺序、阶段时间和预测快照。

能够由已安装目录识别的历史模型关联其插件计时策略；未知模型保留在禁用的历史归档下，不进入其他插件的校准。已删除任务的匿名样本继续保留；物理删除任务仅清空计时的任务关联。历史任务仍绑定禁用的归档连接，导入不会恢复节点凭据或启用任何真实提供方。

早期导出若未包含 `job_runs`，不会编造阶段时间或样本。需要完整计时历史时，应从一致性备份重新导出，并在新的隔离目标数据库验证；现有导入仍拒绝相同来源内容变化，不能靠覆盖用户数据补齐历史。

## 验证

```sh
pnpm test
pnpm test:timing
pnpm test:provider-clock
```

`test:timing` 使用固定原 Python 3.12 环境 `.runtime-advanced/original/.venv/bin/python`，在临时 SQLite 数据库计算参考结果。新实现使用临时 PGlite，或 `TEST_DATABASE_URL` 上的独立随机 PostgreSQL schema。不会调用真实模型、GPU 或支付。

当前对照包含 156 个估算/进度场景、123 组提供方/硬件特征和 41 个执行状态快照，全部严格相等；另检查计时导出不含节点密钥及拒绝活动记录。包含 worker 浮点区间恰好超过接收上限的边界，保留 Python 3.12 补偿求和后的判定。`pnpm test` 增加 7 项集成测试，覆盖旧版本取消兼容、当前租约、重复回传、结算、进度单调、中断恢复、历史迁移、匿名样本和全局 500 条边界。

`test:provider-clock` 在临时 SQLite 中直接调用原 `muse_provider.sync_timing`，比较 141 个场景、145 个数据库/耗时/剩余时间快照。覆盖排队到完成、原阶段映射、时间边界、耗时回推、重复报告、终态记录、已记录接收时间、错误类型及清除过早本地生成时间。额外的假 HTTP 提供方测试走实际提交/轮询/私有产物保存与积分结算，并验证旧版本请求、过期回调和未声明能力的拒绝。不会调用真实 Muse。

多实例分支预测及 Muse/Flow 容量规则已作为 `1.3.0` 可选插件能力迁移，Muse 上游阶段/开始时间同步由 `1.4.0` 提供。仍需完成：原任务与状态 HTTP 契约、完整 Muse 准入错误/重试及状态说明、旧 worker/并行通道、真实执行端遥测，以及原工作台 React 交互和视觉验收。默认 `/studio` 仍走原兼容业务后端，不表示技术栈迁移完成。
